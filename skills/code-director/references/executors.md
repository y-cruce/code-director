# Executors other than Codex

Use Antigravity (`agy`) first for investigation, debugging and implementation, backend and frontend alike, unless the user chooses another executor. Omitted `executor` uses `$CODEX_DIRECTOR_EXECUTOR`, else Codex; explicitly use `executor: "codex"` when required. Reviews stay on Codex. Both `continue` and `fork` ignore this default and restore their thread's executor, command and arguments; explicit mismatches are rejected. Set `executor` on `mcp__codex__dispatch` (the `EXECUTOR:` Bash header).

| `executor` | Agent | `fork` (`mode: "fork"`) | Extra fields |
|---|---|---|---|
| `codex` | Codex through the plugin's app-server | Supported (`thread/fork`) | — |
| `qoder` | qodercli over ACP; found on PATH, then `~/.qoder/entry/qoder`, or `CODEX_DIRECTOR_QODER_COMMAND` | Supported (`session/fork`) | `executor_mode` (a Qoder session mode, e.g. `yolo`) |
| `dsh` | DeepSeek Harness over ACP; executable from `executor_command`, `$CODEX_DIRECTOR_DSH_COMMAND`, then PATH `dsh`; default args from `$CODEX_DIRECTOR_DSH_ARGS`, else `acp-fork` when that profile is installed in `$DSH_HOME` and `acp` otherwise | Supported on `acp-fork`; unsupported on `acp` | `executor_args`, `executor_mode` (`default` or `plan` on the community profile), `executor_permissions` (`allow-once` or `ask`) |
| `antigravity` (alias `agy`) | CLI `agy acp`; executable from `executor_command`, `$CODEX_DIRECTOR_ANTIGRAVITY_COMMAND`, then `~/.local/bin/agy` or PATH | Unsupported (`agy acp` 1.5.6 lacks `session/fork`) | `executor_args`, `executor_mode`, `executor_permissions` (`allow-once` or `ask`), `swarm` (optional, new `investigate`/`implement` only) |
| `cca` | Claude Code over ACP (`claude-agent-acp`); executable from `executor_command`, `~/.local/bin/cc-acp`, then PATH `claude-agent-acp` | Supported (`session/fork`) | `executor_args` (`[]` by default), `executor_mode` (`bypassPermissions` by default), `executor_permissions` (`allow-once` by default, or `ask`), `model`, `executor_effort` |
| `acp` | Any other agent speaking the Agent Client Protocol on stdio | Supported when `sessionCapabilities.fork` is advertised | `executor_command` (or `$CODEX_COMPANION_ACP_COMMAND`; one of them is required), `executor_args` (an array of strings), `executor_mode` |

`fork` checks capability at runtime: ACP drivers inspect `agentCapabilities.sessionCapabilities.fork` after `initialize` and reject unsupported agents with `UNSUPPORTED_CAPABILITY`; older Codex CLI versions returning `-32601` on `thread/fork` report an upgrade message. After `session/fork` returns the new session id, ACP `fork` re-applies the inherited or overridden `mode`, `model` and `effort` because some ACP servers (such as DSH) reset forked sessions to their default model.

For running corrections, use the same default `delivery: "steer"` as Codex when the job reports `midTurnSteer: true`. Qoder and agy support this natively; cca and DSH use the extension below. `queue` means a later turn; ACP transport alone is no reason to select it. A finished job is continued with `continue`.

**Qoder.** `model` names Qoder's own model (`dfmodel`, `fast`, `ultimate`); without it a task runs on the default in Qoder's settings, and `continue` keeps the model its thread was created on. Qoder runs in its `yolo` permission mode by default, so a dispatched task never stalls on a prompt no human is watching; `executor_mode` overrides it.

For mid-turn messages, Qoder advertises its private `agentCapabilities._meta.qoder.promptQueueing` capability. A supporting plugin sends another `session/prompt` to the same session while the current prompt is running; Qoder can consume it at a loop boundary. Use default `delivery: "steer"` only when the plugin reports `midTurnSteer: true`. `queue` is for an intended next turn. If an older plugin lacks steering, choose queue or interrupt by the correction's intent. Submission does not prove model consumption. Qoder does not implement the `_session/steering` extension.

**DSH.** Lookup order is explicit `executor_command`, `$CODEX_DIRECTOR_DSH_COMMAND`, then `dsh` on PATH. Default arguments come from `$CODEX_DIRECTOR_DSH_ARGS` (a JSON array) when set; otherwise `["--profile","acp-fork"]` when the `acp-fork` profile is installed in `${DSH_HOME:-$HOME/.dsh}/profiles/acp-fork`, and `["--profile","acp"]` otherwise. Explicit `executor_args` overrides any default. The stock `acp` profile has no session modes, so `executor_mode` is rejected when only that profile is available.

The `acp-fork` profile runs the community plugin `@8kugames/dsh-zed-acp` (`0.3.11`, peers `~0.2.2-rc.2`) inside the one global dsh installation (`0.2.2-rc.5`), sharing `~/.dsh` with the web UI and the stock `acp` profile. (Until 2026-11-23 it was an isolated runtime under `~/.local/share/dsh-fork` because the plugin's peer range did not match the older global dsh; that reason is gone and the isolated copy was retired.) Its modes are `default` and `plan`; omit `executor_mode` for the profile default. Leave `model` out to keep the selected profile's configured model; an explicit value must be an advertised ACP model id. The default `executor_permissions: allow-once` selects only an offered one-shot allow option; `ask` forwards permission choices to you. Continue with the returned thread and omit launch overrides: its recorded command and arguments are restored, including the old launcher for existing DSH threads. After the worker closes, continuation uses `session/resume` and the plugin replays its saved events.

The community plugin implements `_session/steering` and advertises it under `agentCapabilities._meta.steering`. Steering appends to the active turn; the original `session/prompt` response still ends that turn. It also provides `session/load`, whole-session `session/fork` (used by `mode: "fork"` / `task --fork-thread <id>`) and inclusive forking at an assistant reply; ACP `fork` re-applies `mode`, `model` and `effort` after creating the forked session because DSH resets forked sessions to the default model. Tasks using the community adapter use its built-in steering; the old global `dsh-plugins/acp-steering` patch is needed for steering with the original ACP adapter.

For director questions use `node "$CODEX_ACP_COMPANION_PATH" ask-director --question "Question" --options '["First","Second"]'`. It uses the same pending-question, answer and ten-minute timeout path as ACP native questions and prints the answer, including free text, to stdout. With dsh bash, use `timeoutMs:600000`; the default is 120000 ms, capped at 600000 ms. A composition with jobs promotes a still-running foreground command on timeout; collect it with `job_output`, not a new question. Without jobs the shell may kill it at that limit, slightly before the companion's deadline; report the shell outcome and check status.

To opt into the fork-capable adapter, add the plugin as a profile of the global installation (dsh `>= 0.2.2-rc.2` is required by the plugin's peers):

```sh
dsh plugin --profile acp-fork add @8kugames/dsh-zed-acp@0.3.11
```

Then populate `~/.dsh/profiles/acp-fork/cordis.patch.yml` with the provider rows and the default model the profile should use (the `dsh-base` bundle already provides the stock plugins; `dsh-zed-acp` adds the ACP bridge). A `zed-acp` entry with `modelPreferencePath: !!js dshHomePath('zed-acp-reasoning-efforts.json')` keeps the effort preference in `$DSH_HOME`. Credentials come from the usual `~/.dsh/.credentials.yaml`; nothing is duplicated.

Dispatch then runs `dsh --profile acp-fork` (or the `~/.dsh/bin/dsh-acp` wrapper with the same arguments) and shares the session store with the web UI, so dispatched threads show up in the web sidebar and the write lock released by the idle-release patch applies to both. To fall back to the stock adapter, specify `dsh` as `executor_command` and `["--profile","acp"]` as `executor_args`.

**Antigravity.** By default it follows the model and effort configured in `~/.gemini/antigravity-cli/settings.json` and is strong at complex coding tasks and frontend design and implementation, so tasks whose hard part is design or implementation go to it, frontend tasks included. `model` or `$CODEX_COMPANION_ANTIGRAVITY_MODEL` overrides the model. Use the installed CLI's `agy acp` (verified with 1.5.6); it reuses the CLI login and MCP configuration. The preset prefers `~/.local/bin/agy` over PATH terminal wrappers, and defaults arguments to `["acp"]`. The subprocess inherits the companion's network environment. Leave `executor_mode` out for the server default, or select `default`, `accept-edits`, `auto` or `plan`. Permissions default to `allow-once`. Continue restores the recorded executable and arguments.

`antigravity` is the canonical executor name and `agy` is an equivalent alias, including in dispatch fields and Bash headers. Both produce the same ACP launch configuration, so either can continue a session created under the other name. If an installed plugin's dispatch schema lacks both names, use `executor: "acp"`, the absolute server path as `executor_command`, `executor_args: ["acp"]` and `executor_permissions: "allow-once"`. The updated Bash skill accepts either preset name with that plugin.

The CLI reads `~/.gemini/config/mcp_config.json` itself, including HTTP `serverUrl` entries. No separate helper or MCP alias conversion is needed.

New and resumed agy sessions include HOME and linked skill directories alongside the existing additional directories. The appended system prompt directs shell commands to the task's cwd. The CLI no longer generates the old workflow skill; the plugin no longer writes its Git exclusion.

agy native form questions always wait for the director, including under allow-once. Ordinary tool permissions still follow allow-once/ask. Without a model override, new sessions follow `~/.gemini/antigravity-cli/settings.json` for both model and effort; an explicitly chosen model defaults to high, Opus to medium (when offered); `continue` does not impose a default effort.

Install the shared `codex-executor` skill under `~/.gemini/antigravity-cli/skills/codex-executor`; both the CLI and official ACP server read that user skill directory. Link the whole skill directory so its `scripts/context.sh` remains available. Dispatched tasks also receive the skill's absolute source path in the director note.

**agy swarm (`swarm: true` / `SWARM: yes`).** Supported on new `investigate` or `implement` tasks dispatched to `agy`/`antigravity` (rejected on other executors or `continue`/`fork`/`review`). `dispatch.sh` places `/swarm ` at byte 0 of the prompt so `agy acp` expands the native swarm coordinator skill, and appends a swarm-specific director note at the end: it allows coordinator delegation, suppresses the headless-unused `narrator` (keeping `monitor`), instructs the coordinator to include the absolute `cwd` in every worker brief (workers inherit all workspace roots without the appended system prompt), keeps workers on `workspace: "inherit"` with disjoint file/directory ownership (multi-root ACP sessions include non-Git skill directories, causing agy's `workspace: "share"`/`"branch"` to fail), and asks the coordinator to post `[done]` and consolidate director questions. `agy acp` keeps the single `session/prompt` turn open across multi-hop worker wakeups and returns one combined usage total when the coordinator finishes; the plugin splits interim coordinator replies from the final delivery and renders readable swarm tool titles and member statuses in the tasks pane. While workers run, the main ACP stream emits no updates, so `status` automatically reads `~/.gemini/antigravity-cli/brain/<threadId>/.system_generated/swarm/` (and active worker transcripts) to show the member roster, recent board posts, and real progress age. For long swarms, briefs can also ask the coordinator to send brief milestone updates via `notify-director` (in addition to blockers, quota model switches, or stalled fix loops).

**agy steering.** The CLI accepts a concurrent `session/prompt` as input to the active conversation. It settles the previous prompt on steering; the driver waits for the latest response before completing the same job and turn. Submission does not separately acknowledge acceptance or model consumption.

Steering works while agy's prompt is active, including while foreground or background commands run. If the CLI returns `end_turn` before finite commands finish, the job stays running, reads their statuses through `session/load`, and automatically prompts the agent to finish the original task once they complete. The driver refuses steering during the wait. Use queue for the next turn or interrupt to stop the wait and correct immediately. Background commands keep running after interrupt unless the new instruction stops them. Repeated waits share 30 minutes. On timeout, the driver reports the remaining commands. Native `IsDaemon: true` commands are excluded. DSH retains the original prompt boundary.

**Claude Code ACP (`cca`).** Lookup order is explicit `executor_command`, executable `~/.local/bin/cc-acp`, then `claude-agent-acp` on PATH. Default arguments are `[]`, default `executor_mode` is `bypassPermissions`, and default `executor_permissions` is `allow-once`. New sessions without an explicit `executor_effort` pick their default in the driver from the active model's name (or `description` on `default` rows): DeepSeek Flash defaults to `max`, and GLM-5.4 or other models default to `high` (skipped when the model exposes no `effort` option). Because `claude-agent-acp` applies effort in process memory only, `cca` `continue` re-applies the thread's last confirmed `executorEffort` unless explicitly overridden. `cca` supports `session/resume`, `session/fork`, `_session/steering` (`midTurnSteer: true`), and native `AskUserQuestion` forms via elicitation.

**ACP steering extensions.** A server advertises these with `_meta.steering.supported: true` at the initialize response's top level or under `agentCapabilities`. The plugin sends `_session/steering` with the current session, prompt and `_meta.steering.idleBehavior: "promptRequired"`. `injected` confirms insertion, not model consumption; `promptRequired` consumes nothing and asks the client to deliver a normal prompt later. A null or unrecognized outcome does not establish insertion. The DSH community plugin and `claude-agent-acp` (`cca`) include this extension; other servers need their corresponding extension.

The task-control endpoint is exposed in the ACP executor's environment and permits answer and approval calls; this relies on the executor not invoking those interfaces on its own.

Antigravity CLI setup and rollback details are in the plugin's `scripts/agy-acp/README.md`. DSH's community adapter is [@8kugames/dsh-zed-acp](https://github.com/8kugames/dsh-zed-acp).

**What you lose off Codex:**

- Native `review` and `adversarial-review` modes are refused: they use Codex's own review, which has no ACP equivalent. Frontend reviews still go to agy as `investigate` tasks with a read-only review brief.
- `effort` does not reach the agent. ACP uses `executor_effort` (or `$CODEX_DIRECTOR_EXECUTOR_EFFORT`) with values advertised by the agent.
- ACP notes use `node "$CODEX_ACP_COMPANION_PATH" notify-director "message"`; they produce the same `director.notified` event as Codex and continue working. agy/Qoder/cca use native questions; dsh uses `ask-director`. Question and permission requests expire after ten minutes and interrupt the active turn. Only Monitor mode sends periodic unanswered-question reminders.
- Use default steering with Qoder, agy, cca, and DSH with its extension when `midTurnSteer: true`. If the executor rejects steer or lacks that capability, use queue for a later turn or interrupt when active work must stop.
- A thread belongs to the executor that created it: a Qoder session id cannot be resumed as a Codex thread.
- ACP interrupt preserves edits but reports no partialChanges. Active ACP queue starts a separate job per instruction and returns `queuedJobId`; active Codex queue stays in the same job. Idle queue returns a new job for either executor. Steer is rejected while a question is pending; queue is allowed.
- Default full access already permits writes even without `write:true`. Express read-only intent in the brief. ACP does not enforce Codex sandbox flags; its own permissions/modes apply, and Qoder ask does not remove its default bypass mode.
- The live view depends on the agent: command-output deltas and a complete turn diff may be unavailable, and Qoder sub-agent rows do not provide Codex's full child-thread events. Missing usage or an agent-reported zero does not prove zero consumption. The result footer prints `Session ID:` with no `codex resume` line. Claude transcript transfer remains Codex-only; there is no session/load fallback or numeric/boolean form conversion.
